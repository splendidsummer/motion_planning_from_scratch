# RRT：带夹爪 Gento Skye 的桌面避障规划

[返回目录](README.md)。本文只讨论 [桌面场景脚本](../docs/scene_gento_skye.py) 和本项目的 MoveIt / RViz 配置，不使用二维点机器人示例。启动环境见 [RViz 使用说明](../docs/gento_skye_rviz.md)。

## 1. RViz 中的桌子是否真的参与碰撞检测？

**参与，前提是场景已成功提交给 MoveIt 的 PlanningScene。** `apply_scene()` 通过 `/apply_planning_scene` 添加 `CollisionObject`，不是只画 RViz Marker。所有物体都以 `base_link` 为坐标系，长度单位为米。

| 碰撞对象 | 实际几何与位置 |
|---|---|
| `table_top` | 白色桌板，尺寸 1.50 × 2.40 × 0.05，中心 (1.25, 0, 0.335)，上表面 z = 0.36 |
| `table_legs` | 一个复合对象：尺寸 1.62 × 2.52 × 0.03、中心 (1.25, 0, 0.295) 的灰色整块底板，加上四条桌腿；并非空心边框 |
| 四条桌腿 | 各为 0.09 × 0.09 × 0.28，中心 x = 1.25 ± 0.71、y = ±1.16、z = 0.14 |
| `cube` | 边长 0.06，中心 (0.70, 0, 0.39)，底面与桌面上表面齐平 |
| `ball_right` / `ball_left` | 中心 (0.45, ∓0.55, 0.86)，半径 0.07 |
| `ball_high_right` / `ball_high_left` | 中心 (0.62, ∓0.28, 1.02)，半径 0.06 |
| `ball_front` | 中心 (0.90, 0, 0.98)，半径 0.07 |

仅启动 RViz 不等于已经添加这张桌子。运行场景脚本、确认场景服务成功，并在 RViz 的 PlanningScene 显示中核对上述对象。RViz 用来显示；规划所依据的是 `move_group` 持有的场景。

## 2. 规划的是双臂关节，不是一个 TCP 点

[SRDF](../gento_skye_moveit_config/config/gento_skye.srdf) 决定哪些关节一起规划、底座如何固定，以及哪些连杆对跳过碰撞检查，说明见 [SRDF 说明](../docs/srdf.md)。其中 `right_arm`、`left_arm` 各有 7 个活动关节，`both_arms` 合计 14 个。桌面脚本的三个手臂运动阶段都请求 `both_arms` 规划：

$$
q=(q_{1,R},\ldots,q_{7,R},q_{1,L},\ldots,q_{7,L})\in\mathbb{R}^{14}
$$

夹爪不在这 14 个搜索变量中，但**夹爪不参与搜索，不等于夹爪不参与碰撞检测**。指爪的 collision 网格定义在 [机器人 URDF](../gento_skye_moveit_config/config/gento_skye.urdf) 中，会随手臂运动。每侧夹爪含两个滑动关节，其中一个 mimic 另一个；脚本使用 0 表示闭合、0.04 m 表示打开。

每个手臂规划请求把夹爪开度固定在该阶段的值。MoveIt 根据完整机器人状态计算运动连杆及夹爪的位置，检查与桌板、底板、桌腿、球、方块的碰撞，以及适用的机器人自碰撞。腰、头和其他非规划关节不由这次 RRT 搜索主动调整。

碰撞检查受允许碰撞矩阵（Allowed Collision Matrix，ACM）约束。这张表在加载 [SRDF](../gento_skye_moveit_config/config/gento_skye.srdf) 时由 `disable_collisions` 构成，场景脚本没有再把桌子放进表里。构成规则见 [SRDF 说明](../docs/srdf.md)。不能把“状态有效”理解成所有网格两两都检查过；也不能为了规划成功而把夹爪与整张桌子的碰撞一并允许。

## 3. RRT 在这张桌子旁如何扩展？

RRT（Rapidly-exploring Random Tree）从起始双臂构型长出一棵树。一次扩展：

1. 在关节限位内采样 `q_rand`；目标偏置时改为采样目标区域中的构型。采样方向本身不保证无碰撞。
2. 在树中找到最近构型 `q_near`。
3. 沿关节空间方向走不超过 `range` 的距离，得到 `q_new`。
4. 检查从 `q_near` 到 `q_new` 的运动；通过后才把新节点和这条边加入树。

记 η 为 `range`，在这里的欧氏关节空间解释下：

$$
q_{\mathrm{new}}=q_{\mathrm{near}}+
\min\left(1,\frac{\eta}{\|q_{\mathrm{rand}}-q_{\mathrm{near}}\|_2}\right)
(q_{\mathrm{rand}}-q_{\mathrm{near}})
$$

采样点与最近点重合时不需要按这个式子除以零，直接跳过扩展。**关节空间中的直线，不代表 TCP 或夹爪在桌面上方走直线。** 肘部可能向桌边扫去，指尖也可能先下降再上升。

脚本用 IK 生成关节目标，并为各目标关节设置 ±0.05 rad 的容差。RRT 要到达的是满足请求约束的目标区域，而不是“距离目标小于 `range` 就算到达”。从满足目标的节点沿父节点回溯，可得到一条关节路径；基础 RRT 不保证最短路径。

## 4. “沿途碰撞检查”在桌面场景中具体检查什么？

假设 `q_near` 时夹爪在桌边上方，`q_new` 时夹爪已经移到方块附近。**即使这两个端点都不碰撞，中间运动也可能让指尖穿过白色桌板，或让前臂撞上障碍球。** 起点检查、目标 IK 的避碰检查都不能替代这条边的检查。

MoveIt / OMPL 的常规离散运动检查沿关节空间插值：

$$
q(s)=(1-s)q_{\mathrm{near}}+s q_{\mathrm{new}},\qquad 0\le s\le1
$$

对检查到的中间构型，更新机器人正运动学和碰撞几何，按规划组及 ACM 规则查询碰撞。对于桌面任务，重点包括：

- 指尖和夹爪本体是否进入 5 cm 厚的白色桌板、其下的灰色底板，或方块。
- 前臂、肘部等运动连杆是否撞到球或桌腿；只看 TCP 高度不够。
- 两只手臂和夹爪在向方块靠拢时是否互相碰撞。

检查过程中发现无效状态，这次扩展就会被拒绝。中间检查点不一定作为 RRT 树节点或最终显示轨迹的路点保存，不能靠 RViz 显示的路点数量推算碰撞检查次数。

**这里是按分辨率进行的离散检查，不是完整连续扫掠体检测。** 中间采样太疏仍可能漏过薄桌板或小间隙；“检查通过”不等于数学上证明任意时刻都无碰撞。

### 哪些设置控制检查精细程度？

[当前 OMPL 配置](../gento_skye_moveit_config/config/ompl_planning.yaml) 没有显式设置 `longest_valid_segment_fraction`、`maximum_waypoint_distance` 或 RRT 的 `range`。因此不能仅凭仓库文件宣称当前每隔多少弧度、多少毫米检查一次；实际值还要核对正在运行的 MoveIt / OMPL 版本与加载参数。

| 设置或数据 | 含义 | 不代表什么 |
|---|---|---|
| `range` | RRT 一次扩展的最大状态空间距离 | 不是碰撞检查间隔 |
| `longest_valid_segment_fraction` | 相对状态空间最大尺度的离散检查分段比例 | 不是相对桌板厚度的比例 |
| `maximum_waypoint_distance` | 支持该设置的 MoveIt OMPL 接口中，限制离散检查分段的绝对状态空间距离；与比例限制一起使用时取更严格者 | 不是 TCP 位移的米数 |
| 速度、加速度限制及时间参数化 | 为几何路径分配运动时间 | 不能替代几何碰撞检查 |
| RViz 播放速度、显示路点 | 可视化行为 | 不是规划检查精度或真实控制周期 |

用简单欧氏空间来理解，若最大状态空间尺度为 D、比例为 f，则检查分段长度尺度约为 δ = fD。一条长度为 L 的边需要约 `ceil(L / δ)` 段；具体分段还受状态空间实现及其他限制影响。

例如，**仅作计算示例，并非当前运行值**：若双臂 D ≈ 17.92、f = 0.01，则 δ ≈ 0.179，长度 3.58 的边约分为 20 段。但 0.179 是关节空间长度，不是 17.9 cm；没有正运动学和连杆几何，不能据此断言不会穿过 5 cm 厚的桌板。

桌边、桌面和指尖附近需要更细的验证。应在相同场景与轨迹上逐步加密检查，观察是否出现新增碰撞，并保留几何安全间隙；即使加密后没有发现碰撞，也不构成真机安全认证。

## 5. 双臂步长 3.58 为什么仍然很大？

此前的 3.58 来自如下估算：按关节限位盒子的欧氏对角线计算单臂尺度约 12.67，双臂尺度再乘 √2；若 RRT 使用 OMPL 常见的 0.2 倍尺度自动设置，则：

$$
\eta\approx0.2\times12.67\times\sqrt{2}\approx3.58
$$

这是基于上述空间和默认机制的估算，不是从当前 `move_group` 读取的实测参数。位置上下限来自 [机器人 URDF](../gento_skye_moveit_config/config/gento_skye.urdf)；[关节限制配置](../gento_skye_moveit_config/config/joint_limits.yaml) 当前主要设置速度和加速度，不能通过降低速度来缩短 RRT 扩展距离。

假设用满这一步，且 14 个关节的变化量绝对值都为 a，则：

$$
\|\Delta q\|_2=\sqrt{\underbrace{a^2+\cdots+a^2}_{14\text{ 项}}}
=\sqrt{14}\,a,
\qquad a=\frac{3.58}{\sqrt{14}}\approx0.96\ \text{rad}\approx55^\circ
$$

这就是除以 √14 而不是 14 的原因：欧氏长度是平方和再开方。实际扩展不会刻意平均分配各关节变化量。**约 55° 仍然很大，这个换算并不是说默认步长适合桌面操作。**

通用尺度比例不根据桌板厚度、双臂间隙或指尖到方块的距离调整。大步长可能在开阔区域更快，在桌边却频繁扩展失败；小步长可能便于局部探索，但会增加树节点和查询开销。

可把 `range = 0.3、0.5、1.0` 作为待验证的对比候选。η = 0.5 时，等幅变化的例子为每关节 0.5 / √14 ≈ 0.134 rad ≈ 7.7°。这些不是已验证的推荐参数，更不是安全阈值。比较时固定桌面场景、起终点、夹爪状态、碰撞检查分辨率和规划预算，多次统计成功率与耗时。

## 6. 当前抓取动画有哪些尚未完整验证的部分？

[桌面脚本](../docs/scene_gento_skye.py) 的流程是三个独立的双臂规划请求，再拼接夹爪动作。五段的起终点、检查范围和下面这些边界的对照见 [抓取拼接轨迹](../docs/grasp_trajectory.md)。

| 阶段 | RRT 搜索变量 | 规划时夹爪状态 |
|---|---|---|
| `approach`：初始状态到预抓取位姿 | 14 个手臂关节 | 闭合，0 m |
| `ramp_grippers()`：打开 | 不调用 RRT，直接插入动画点 | 从 0 到 0.04 m |
| `move_in`：向抓取位姿靠近 | 14 个手臂关节 | 打开，0.04 m |
| `ramp_grippers()`：闭合 | 不调用 RRT，直接插入动画点 | 从 0.04 到 0 m |
| `lift`：撤退 | 14 个手臂关节 | 闭合，0 m |

需要明确以下边界：

1. **手臂路径的检查不覆盖后来插入的夹爪开闭全过程。** `ramp_grippers()` 在 0.8 秒内插入 6 个点，但没有调用碰撞检查；点数多不代表经过验证。夹爪张开或闭合时也可能扫到桌子、方块或另一只手。
2. **三个请求拼接后没有对整条轨迹重新做完整验证。** 目标有 ±0.05 rad 容差，上一段实际终点可能不等于下一段使用的名义起点；段间连接也需要检查。
3. **撤退失败时有移除方块的回退逻辑。** 脚本临时从 PlanningScene 删除 `cube` 后重试，再恢复方块。重试成功仅意味着对当时没有方块的场景通过规划，不能声称对原场景也通过了验证。
4. **方块“随手移动”是回放逻辑，不是已规划的附着物体。** 回放时脚本把世界中的方块移动到两个 TCP 的中点，没有以 `AttachedCollisionObject` 建模随手搬运的物体；不能据此声称已验证搬运物体与桌子、球和机器人的碰撞。
5. **当前是 RViz 显示与模型回放，不是真机控制。** 脚本发布 `/display_planned_path` 与 `/joint_states`；[启动配置](../gento_skye_moveit_config/launch/demo.launch.py) 和 [控制器配置](../gento_skye_moveit_config/config/moveit_controllers.yaml) 未建立真机执行链路。

若要将演示变成经过完整碰撞验证的抓取流程，还需要验证夹爪开闭与段间连接、正确建模抓取物体及必要的 `touch_links` / 接触许可，并针对最终拼接和时间参数化后的轨迹复核。双臂协同抓持还需表达相应约束，不能用删除方块代替这些步骤。以上是当前代码的限制，不是已经完成的功能。

## 7. 在 RViz / MoveIt 中如何核对结果？

- 先启动 MoveIt 演示，再运行桌面脚本。脚本默认选择 `RRTConnect`；要研究本文算法，需选择 `--planner RRT`。RViz 手动请求时也应确认选中 `both_arms` 和正确的规划器，运行日志用于核实最终采用的规划器。
- 检查 `scene=table,cube,balls`、`start_valid`、`goal_valid` 和各阶段 `error_code`；端点有效只是必要条件，不代表整条运动有效。
- 核对实际加载的机器人碰撞模型、ACM、规划器参数和离散检查分辨率。夹爪开度应与对应规划请求一致，不只看 RViz 中当前显示的开度。
- `--time` 传给每个阶段请求的 `allowed_planning_time`，不是整段演示的总耗时，也不是机器人运动时长。脚本还请求多次规划尝试，IK、服务等待和回放另有耗时。
- [OMPL 配置](../gento_skye_moveit_config/config/ompl_planning.yaml) 启用 `AddTimeOptimalParameterization`，各阶段速度与加速度缩放为 0.25；这不消除上面列出的拼接、夹爪和搬运验证缺口。

**总结：对于这张桌子，“沿途检查”是检查整个运动机器人（包括固定开度的夹爪）在关节插值状态下与 PlanningScene 的碰撞，不是只检查 TCP 或终点。当前手臂规划包含离散运动检查，但整段抓取动画尚不能视为经过完整碰撞验证的执行轨迹。**
